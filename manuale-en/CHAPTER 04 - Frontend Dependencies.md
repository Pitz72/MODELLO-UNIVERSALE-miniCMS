# CHAPTER 4: Frontend Dependencies

Frontend dependencies are architectural choices, not just lines in `package.json`. Every library you add has a cost (bundle size, update surface, integration complexity) and has to earn its place. This chapter documents the choices made across the four reference sites, with the reasoning behind them, and it gives equal space to an absence: the libraries the Model chooses **not** to use.

## 1. The Core Stack (Every Project)

These dependencies are present in all four sites, no exceptions:

| Library | Version | Role |
| :--- | :--- | :--- |
| `react` + `react-dom` | ^19.2.x | UI framework: components, state, rendering |
| `react-router-dom` | ^7.x | Client-side routing, React Router v7 (stable API) |
| `typescript` | ~5.x | Compile-time type safety |
| `vite` | ^7.x | Build tool: HMR dev server, optimized bundle |
| `@vitejs/plugin-react` | ^5.x | Vite plugin for the JSX/TSX transform |
| `lucide-react` | ^0.5xx | Tree-shakeable SVG icons, native to React |

React 19 brings improvements to concurrent rendering and Server Components. For the Universal Model (a client-side SPA only), the practical difference from v18 is small, but staying on the latest stable version is the right call for new projects.

### 1.1 The Absence That Counts: No Data-Fetching Libraries

Before listing what’s there, it’s worth listing what’s missing, because that’s as much a choice as the rest. None of the four sites use a data-fetching or state-management library: no Axios, no React Query, no SWR, no Redux, no Zustand. The bridge to the PHP backend is the `api` object, a thin wrapper over native `fetch` (Chapter 6); shared state lives in the router (SimonePizziWebSite, with React Router’s loaders) or is component-local `useState` (SitoRuntime and DISINTELLIGENZA).

It isn’t laziness, it’s consistency with the philosophy of Chapter 1: every dependency you don’t add is an update surface you don’t have to maintain, a bundle that doesn’t grow, a behavior you don’t have to learn. `fetch` does almost everything a CMS needs; the little it lacks (a single place for errors, an interceptor for an expired session) takes a few lines to write, and Chapter 6 tells the story of where the sites chose not to write them.

## 2. Tailwind CSS: v3 vs. v4

The four sites use different versions of Tailwind, with noticeably different configuration.

### SitoRuntime: Tailwind v3 (classic setup)

```json
// devDependencies
"tailwindcss": "^3.4.17",
"autoprefixer": "^10.4.22",
"postcss": "^8.5.6"
```

It requires explicit `tailwind.config.js` and `postcss.config.js` files. The entry CSS:
```css
@tailwind base;
@tailwind components;
@tailwind utilities;
```

### SimonePizziWebSite, DISINTELLIGENZA, FDCA: Tailwind v4

```json
// devDependencies
"tailwindcss": "^4.x",
"@tailwindcss/vite": "^4.x"  // or "@tailwindcss/postcss"
```

Tailwind v4 uses the native Vite plugin: no separate `postcss.config.js`, no mandatory `tailwind.config.js`. The CSS:
```css
@import "tailwindcss";
```

For new projects, the choice is v4. Migrating from v3 takes some care with renamed classes (for example, `shadow-sm` became `shadow-xs`).

### @tailwindcss/typography

Present in every site as a devDependency. It adds the `prose` class, which applies polished typographic styles to blocks of dynamically generated HTML (the output of a rich-text editor, or of a Markdown converter).

```html
<div class="prose prose-invert max-w-none">
  <!-- HTML generated by Tiptap or showdown -->
</div>
```

## 3. Content Editing and Rendering

### Tiptap v3: the flagships’ rich-text editor

**Used in:** SimonePizziWebSite and SitoRuntime (the two sites with an editorial workflow).

The rich-text editor on the two flagships is **Tiptap v3**, not a monolithic editor but a set of `@tiptap/*` packages that compose like building blocks: about a dozen modules for the core and the extensions actually in use.

```json
"@tiptap/react": "^3.x",
"@tiptap/pm": "^3.x",
"@tiptap/starter-kit": "^3.x",
"@tiptap/extension-image": "^3.x",
"@tiptap/extension-text-style": "^3.x",
"@tiptap/extension-color": "^3.x",
"@tiptap/extension-text-align": "^3.x",
"@tiptap/extension-table": "^3.x",
"@tiptap/extension-youtube": "^3.x"
```

Tiptap produces **HTML** (not Markdown), which is saved raw in the database and sanitized at render time with DOMPurify (the full treatment, including the link-insertion guards and the sanitization choke point, is in Chapter 8). SitoRuntime got there through a migration: it used Quill before, and the code still carries the marks of that switch (a conversion shim, a few leftover `react-quill` type defs). Those leftovers aren’t the active editor, they’re scars from the migration to Tiptap.

DISINTELLIGENZA uses no editing library at all: its editor is hand-built with `contentEditable` and `execCommand`. It’s the base rung of the scale, with the security consequence Chapter 8 spells out (it’s the only site without DOMPurify).

### showdown: Markdown → HTML

**Used in:** SimonePizziWebSite, SitoRuntime, DISINTELLIGENZA, for content written in Markdown.

```json
"showdown": "^2.1.0",
"@types/showdown": "^2.0.6"
```

```typescript
import showdown from 'showdown';
const converter = new showdown.Converter({ tables: true, strikethrough: true });
const html = converter.makeHtml(markdownContent);
```

HTML generated from untrusted content always has to be sanitized (see below): showdown and DOMPurify travel as a pair.

### dompurify: XSS sanitization

**Used in:** SimonePizziWebSite, SitoRuntime (always paired with the editor or the Markdown converter). **Absent in DISINTELLIGENZA**, and that’s the security hole Chapter 8 documents.

```json
"dompurify": "^3.3.x",
"@types/dompurify": "^3.0.5"
```

```typescript
import DOMPurify from 'dompurify';
const safeHtml = DOMPurify.sanitize(rawHtml);
// Only now is it safe to use dangerouslySetInnerHTML
<div dangerouslySetInnerHTML={{ __html: safeHtml }} />
```

> [!WARNING]
> **Raw HTML plus `dangerouslySetInnerHTML` without DOMPurify is an XSS vulnerability**
> It holds for the output of showdown, of Tiptap, of any source. Saving raw HTML is a legitimate choice (it preserves formatting), but render time is where sanitization becomes mandatory. DISINTELLIGENZA skips this step, and Chapter 8 shows what that means.

## 4. Animations and Visual Effects

### framer-motion

**Used in:** all four sites.

```json
"framer-motion": "^12.x"
```

```typescript
import { motion } from 'framer-motion';
<motion.div initial={{ opacity: 0, y: 20 }} animate={{ opacity: 1, y: 0 }} transition={{ duration: 0.4 }}>
  {/* content */}
</motion.div>
```

framer-motion is heavy (about 100KB gzipped). It’s justified when the animations are part of the site’s visual identity; where they’re marginal, native CSS transitions are the right choice.

### typewriter-effect

**Used in:** SimonePizziWebSite. A typewriter effect for animated headlines, specific to a personal portfolio.

### tailwindcss-animate

**Used in:** DISINTELLIGENZA. A Tailwind plugin with classes like `animate-in`, `fade-in`, and `slide-in-from-bottom`: a lightweight alternative to framer-motion for simple CSS-based animations.

## 5. SEO and Meta Tags

### react-helmet-async

**Used in:** SimonePizziWebSite, DISINTELLIGENZA. It manages `<title>`, `<meta>`, and `<link>` from the React side, for users with JavaScript enabled.

```json
"react-helmet-async": "^2.0.5"
```

The original version (`react-helmet`) is no longer maintained and has memory-leak problems with React 18+; `react-helmet-async` is the active fork, compatible with React 19.

Social and search crawlers don’t run JavaScript, so the meta tags that matter to them are produced by the **PHP SEO Engine** (Chapter 11). The two complement each other, they aren’t alternatives: SitoRuntime, in fact, drops `react-helmet-async` entirely and delegates the whole of SEO to the server-side engine.

## 6. Utilities

### clsx + tailwind-merge

**Used in:** SimonePizziWebSite, DISINTELLIGENZA.

```json
"clsx": "^2.1.1",
"tailwind-merge": "^3.x"
```

`clsx` composes className conditionally; `tailwind-merge` resolves conflicts between Tailwind classes (`text-sm text-lg` becomes `text-lg`). Together they give you the classic `cn()` helper.

### date-fns

**Used in:** DISINTELLIGENZA, to format the festival dates in the frontend. The other sites handle dates on the PHP side (`date()`, `strtotime()`), keeping the client simpler.

## 7. Build-Time Optimization

### sharp

**Used in:** SimonePizziWebSite, as a `dependency` but only in the post-build scripts.

```json
"sharp": "^0.34.5"
```

`sharp` is a Node.js library for high-performance image manipulation; it’s used in the build scripts to optimize static assets. It’s a `dependency` (not a `devDependency`) because the `postbuild` needs it at build time, but it never enters the React bundle: no `.tsx` file imports it. The runtime WebP conversion of uploads, on the other hand, is all on the PHP side with GD (Chapter 7): `sharp` and GD cover two different moments.

## 9. Rules for New Projects

1. **Start from the minimum**: core stack, framer-motion, lucide-react. Add only when the feature genuinely calls for it.
2. **No data-fetching library**: `fetch` and an `api` object are enough (Chapter 6). Adding React Query or Axios is almost always weight that doesn’t pay off in a thin-stack CMS.
3. **showdown always requires dompurify** when the content is user-generated or comes from the database.
4. **Tiptap for rich editing, a `<textarea>` for the rest**: pull in the `@tiptap/*` packages only where editors need a visual editor; for simple input, a textarea keeps the bundle small.
5. **react-helmet-async for client-side SEO, the PHP engine for crawlers**: they complement each other, they aren’t alternatives.
6. **Tailwind v4 for new projects**: simpler configuration; if you migrate from v3, check the renamed classes.

> - For rich editing, use Tiptap (raw HTML saved + DOMPurify at render); a `<textarea>` for everything else.
> - Every dependency has a cost: add it only if it pays off, and tell build time (`sharp`) apart from runtime (`GD`).
